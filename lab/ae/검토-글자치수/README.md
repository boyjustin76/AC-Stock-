# 총괄 검토 요청 — AE 로 옮긴 글자가 3~5px 밀린다

작성 2026-09-03 · 클로드(AE 랩) · **읽고 답만 주시면 됩니다. 다 보시면 이 폴더는 지웁니다.**

관련 기록은 `log/AE-LAB.md` 의 「B — 편당 전체를 AE 컴포지션으로」 절에 있습니다.
이 문서는 그중 **아직 안 고친 것 하나**만 떼어 검토를 받으려는 것입니다.

---

## 1. 무슨 일인가

씬(`scenes/*.scenes.js`)을 AE 컴포지션으로 굽는 파이프라인이 돌고 있습니다. 판정은 눈이
아니라 **렌더러가 낸 같은 프레임과의 픽셀 대조**로 합니다(`tools/ae/diff.mjs`).

지금 남은 가장 큰 차이가 **글자 위치**입니다. 11-4 컷②의 "손익비 1:2" 배지를 실측했습니다
(흰 글자·검은 외곽선의 잉크 상자를 회색 raw 로 뽑아 열/행 투영으로 셌습니다):

```
검은 외곽선 상자   AE 258px  ·  렌더러 257px      → 크기는 사실상 같다
위치               AE 가 오른쪽 +3.5px · 아래 +5px
```

`배지-위AE-아래렌더러.png` 가 그 확대본입니다(4배, 위 AE / 아래 렌더러).

크기가 같으니 **순수한 이동**입니다. 폰트도 맞습니다 — 렌더러의 `fontTagWeight: 500`,
AE 는 `S-CoreDream-5Medium`, 같은 얼굴입니다.

## 2. 왜 밀리나 — 원인 둘

### 가로 +3.5px · 잉크 상자 대 전진폭

렌더러(`src/render/layers.js` cmgBadge)는 판 너비를 **전진폭**으로 잡고 글자를 왼쪽정렬로
그립니다.

```js
const tw = ctx.measureText(L.text).width;   // 전진폭
const bw = tw + padX * 2;
strokeText(ctx, L.text, bx + padX, L.y + 2, { strokeWidth: size * 0.15 });
```

AE 쪽은 전진폭을 알 길이 없어 `sourceRectAtTime`(**잉크 상자**)을 씁니다. 그런데 잉크
상자는 **획이 글자 밖으로 번진 만큼**을 품습니다. 어긋남을 계산하면

```
어긋남 = 획/2 − 왼쪽사이드베어링 = 6.9/2 − 0 ≈ 3.45px
```

**실측 3.5px 과 맞습니다.** 우연이 아니라 이 식이 원인입니다.

### 세로 +5px · em 상자 대 잉크 상자

캔버스 `textBaseline:'middle'` 은 **em 상자** 기준인데, AE 쪽은 잉크 상자 가운데를 씁니다.
잉크 높이는 글자마다 다르므로 폰트·문구마다 어긋남이 다릅니다.

- Gmarket Sans 를 쓰는 주석(`cmgNote`) → 0~1px, 그래서 여태 안 보였습니다
- S-Core Dream 을 쓰는 태그·배지 → **5px**

## 3. 어떻게 고치나

필요한 값은 딱 둘이고, 둘 다 **캔버스만 아는 값**입니다.

| 값 | 쓰는 곳 |
|---|---|
| `measureText().width` (전진폭) | 판 너비, 가로 정렬 기준점 |
| `'alphabetic'` 과 `'middle'` 의 ascent 차 | 세로 베이스라인 보정 |

렌더러가 Playwright 크로미움 위에서 도니, 그 페이지 안에서 재는 수밖에 없습니다.
길이 둘입니다.

### 길 A — 하네스에서 런타임 계측 (제 추천, 공용 코드 안 건드림)

`tools/ae/` 안에서만 합니다. `page.evaluate()` 로 `CanvasRenderingContext2D.prototype`
의 `fillText`/`strokeText` 를 감싸, 렌더러가 **실제로 쓴** `ctx.font` · `textAlign` ·
`textBaseline` · 문구를 그대로 받아 적습니다. 그다음 같은 페이지의 오프스크린 캔버스에서
그 폰트 문자열로 다시 재어 위 두 값을 뽑습니다.

- `src/` 는 **한 줄도 안 바뀝니다.**
- 폰트 문자열을 제가 흉내 내지 않으므로 **중복이 없습니다** — 렌더러가 기본값을 바꿔도
  따라옵니다.
- 어느 레이어의 글자인지는 이미 있는 `--split`(레이어 하나씩 렌더)으로 정확히 짝짓습니다.

단점: 렌더러가 캔버스 API 를 쓰는 방식에 얹혀 있습니다. 렌더러가 나중에 글자를 다른
경로로 그리면(예: 미리 패스로 변환) 조용히 빕니다. 다만 픽셀 대조가 바로 잡아냅니다.

### 길 B — 렌더러가 글자 치수를 1급 내보내기로 제공

`src/render/` 가 "이 레이어의 글자는 여기에 이 치수로 놓인다"를 계약으로 내놓고 AE 는 그걸
읽기만 합니다.

- 계약이 명시적이라 조용히 빌 일이 없습니다.
- **공용 코드가 바뀝니다.** 렌더러가 AE 를 위한 부담을 지게 됩니다.

## 4. 총괄께 묻는 것

1. **A 로 가도 됩니까?** 공용 코드를 안 건드리는 대신, 렌더러의 캔버스 사용 방식에
   얹히는 걸 감수하는 선택입니다. 저는 A 를 권합니다 — 되돌리기 쉽고, 나중에 B 가
   필요해지면 내보내기 쪽 소스만 갈아 끼우면 됩니다.

2. **B 가 낫다면, 계약을 어디에 둘까요?** 렌더러가 프레임을 그리며 부수적으로 뱉는 게
   맞을지, 아니면 별도의 "치수 질의" 진입점이 맞을지 — 이건 렌더러 주인의 판단입니다.

3. **세로 기준을 아예 바꾸는 건 어떻습니까?** 지금 씬은 글자 세로를 `textBaseline:'middle'`
   로 잡습니다. 이게 em 상자 기준이라 AE 와 어긋나는 근원입니다. 씬 쪽에서 베이스라인
   기준으로 통일하면 양쪽이 같은 말을 하게 됩니다만, **씬 좌표가 전부 바뀌므로** 제가
   함부로 건드릴 일이 아닙니다. 안 하는 게 맞다고 보시면 그렇게 두겠습니다.

## 6. 곁들임 — 이번에 옮긴 것

`태그광선-위AE-아래렌더러.png` 는 같은 작업에서 **해결된** 항목입니다. 매수/매도 버튼의
외부 광선(썸네일 PSD 레이어 효과, 검정 18% · 크기 0.114·h · 3번 겹침)이 AE 에 없어 태그가
납작했습니다.

AE 의 **레이어 스타일은 스크립팅으로 못 켭니다** — `enabled` 는 `canSetEnabled` 가 false,
하위 `setValue` 는 "숨겨져 있으므로", `findMenuCommandId("외부 광선")` 은 0, 메뉴 id
9000~9012 도 전부 안 켜집니다(탐침 `tools/ae/jobs/b7_style.jsx` 에 남겨 뒀습니다).
**거리 0 인 그림자 효과**가 같은 그림을 내므로 그걸로 갔습니다. 참고만 하시면 됩니다.
