# 렌더 속도 리뷰 의뢰서

이 문서는 **"차트 컷씬 렌더러를 더 빠르게 만들 수 있나"** 를 다른 모델에게 물어보려고
정리한 것이다. 배경 전체는 `log/WORKLOG.md` (또는 `log/worklog.db`) 에 있고,
여기에는 그 안에 없는 것 — 무엇을 봐 달라는 것인지, 무엇을 이미 재 봤는지,
무엇이 아직 열려 있는지 — 만 적는다.

---

## 1. 무엇을 하는 프로그램인가

해외선물 유튜브 채널에 쓸 **차트 모션그래픽 클립**을 코드로 렌더한다.
대본에 붙은 타임코드에 맞춰 15~45초짜리 컷 몇 개를 뽑고, 프리미어에는 사람이 얹는다.

한 프레임이 만들어지는 길:

```
scenes/*.scenes.js  ──▶  브라우저 캔버스에 그린다      (src/render/engine.js · chart.js · layers.js)
                    ──▶  PNG 한 장으로 뜬다            (page.screenshot)
                    ──▶  ffmpeg 파이프로 흘려 넣는다   (src/render/encode.mjs)
```

프레임 번호를 받아 그리는 **결정적** 렌더다(실시간 재생이 아니다). 그래서 컷을 쪼개
동시에 돌려도 결과가 순차 렌더와 md5 까지 같다 — 이건 실제로 확인했다.

## 3. 재 본 것

### 전체 (2026-08-26, 4코어)

컷 4개 · 956프레임 · 영상 15.95초

| 방식 | 실제 소요 | 캡처 fps |
|---|---:|---:|
| 순차 (`--all`) | 93.0s | 10.3 |
| 컷별 프로세스 4개 동시 | 45.0s | 21.2 |

병렬은 코어 수만큼만 빨라진다. 컷 수보다 코어가 적으면 **가장 긴 컷이 하한**이다.

### 한 프레임 쪼개기 (2026-08-27, 4코어, 120프레임, 각 1회)

`node src/tools/profile-render.mjs "" 120`

| 조각 | 프레임당 | |
|---|---:|---|
| 캔버스 그리기만 (`page.evaluate`) | **2.2 ms** | 사실상 공짜 |
| `page.screenshot({type:'png'})` | **54.2 ms** | ← 캡처 비용의 96% |
| `canvas.toDataURL('image/png')` | 13.1 ms | 그리기 포함. 스크린샷의 1/4 |
| CDP `Page.captureScreenshot` | 50.7 ms | Playwright 왕복을 빼도 거의 같다 |
| ffmpeg `-preset slow -crf 12` (현재) | 30.1 ms | 376 KB |
| ffmpeg `-preset medium` | **14.0 ms** | 383 KB (+2%) |
| ffmpeg `-preset veryfast` | 10.9 ms | 474 KB (+26%) |

읽는 법 두 가지.

1. **그리는 건 안 느리다.** 레이어 코드를 최적화해 봐야 2.2ms 안에서 논다.
   느린 것은 **캔버스를 PNG 로 만드는 일**이다. CDP 로 직접 찍어도 거의 같다는 것이
   그 증거다 — 병목은 왕복이 아니라 PNG 인코딩 자체다.
2. **인코딩 프리셋이 과하다.** 프리미어로 들어가는 중간 소스인데 `-preset slow` 를 쓴다.
   `medium` 이면 절반 시간에 파일이 2% 커질 뿐이다.

숫자는 각 1회 측정이고 4코어 컨테이너라 흔들린다. ffmpeg 항목은 첫 측정에서 66.7ms,
두 번째에서 30.1ms 가 나왔다 — 경합에 민감하다. **다시 재고 시작하는 편이 좋다.**

## 4. 이미 정해져서 바꾸면 안 되는 것

| | 왜 |
|---|---|
| 59.94fps (=29.97×2) 로 렌더 | 대본 타임코드가 29.97 드롭프레임. 프레임 수가 정확히 두 배여야 한다 |
| 1080p 유지 | 채널 최종본은 720p지만 축소는 손해가 없다 |
| 결정적 렌더 (프레임 번호 → 그림) | 이게 깨지면 병렬 렌더의 md5 동일성이 무너진다 |
| 자막·타이틀·로고는 렌더에 안 넣음 | 프리미어 프리셋에 이미 있어 겹친다 |
| 알파 출력은 무손실 (qtrle) | 오버레이용. 손실 압축 불가 |

## 5. 열려 있는 질문

1. **`canvas.toDataURL` 로 갈아타도 되나.** 4배 빠른데 두 가지가 확인 안 됐다 —
   ① 결과가 `page.screenshot` 과 픽셀 단위로 같은가 (색 프로파일·알파 포함)
   ② base64 문자열을 노드에서 디코드하는 비용이 이득을 얼마나 갉아먹나.
   `--format alpha` 의 투명 배경도 같이 봐야 한다.
2. **PNG 를 아예 건너뛸 수 있나.** ffmpeg 에 rawvideo 로 넣으면 인코딩·디코딩이 둘 다
   사라지지만 프레임당 1920×1080×4 = 8.3MB 를 브라우저에서 꺼내야 한다.
   어느 쪽이 싼지 안 재 봤다.
3. **인코딩 프리셋을 무엇으로 둘까.** `medium` 이 공짜에 가까워 보이는데,
   프리미어에서 스크럽할 때 차이가 있는지는 사람이 봐야 한다.
4. **파이프라인을 겹칠 수 있나.** 지금 루프는 그리기 → 캡처 → 쓰기가 한 프레임씩
   완전히 직렬이다. 캡처와 인코딩이 겹치면 둘 중 긴 쪽만 남는다.
5. **컷 수 < 코어 수일 때.** 지금 병렬화 단위가 컷이라 컷이 2개면 4코어를 못 쓴다.
   한 컷을 프레임 구간으로 쪼개 렌더하고 이어 붙이는 게 가능한가
   (결정적 렌더라 이론상 되지만 GOP 경계 문제가 있다).

## 6. 다시 재는 법

```bash
npm install
node src/tools/profile-render.mjs "" 120          # 첫 컷 120프레임
node src/tools/profile-render.mjs cut3-fear 200   # 특정 컷

npm run render -- --config scenes/cmg-20ma-runner.scenes.js --all   # 전체 렌더
npm run render -- --config ... --all --stills 1                     # 구도만 확인
```

측정값을 갱신하면 `log/build_worklog_db.py` 의 `BENCHMARKS` 에 넣고
`python3 log/save.py "…"` 로 굳힌다.

## 7. 리뷰 결과 (2026-08-27 — 이 의뢰서의 질문에 실험으로 답했다)

측정 도구는 `src/tools/exp-capture.mjs`. 조각이 아니라 **실전 루프(그리기→캡처→인코드)**
를 끝까지 돌려 재고, 각 3회 반복했다. 열린 질문 5개의 답:

1. **`canvas.toDataURL` 로 갈아타도 되나 → 갈아탔다.**
   세 캡처 경로(screenshot / toDataURL / getImageData)의 픽셀이 불투명·투명 씬 모두
   **md5 까지 완전 동일**하고, 같은 프레임을 넣은 mp4 출력 파일도 md5 가 같았다.
   base64 전송·디코드를 포함한 실전 비용은 프레임당 23.6ms — 기존 90.2ms 의 1/3.8.
   `capture.mjs` 기본 경로를 교체했고 예전 경로는 `--capture shot` 으로 남겼다.
2. **PNG 를 아예 건너뛸 수 있나 → 못 건너뛴다.**
   getImageData→HTTP→rawvideo 는 프레임당 **746.6ms 로 탈락**. 8.3MB 비압축 전송이
   PNG 인코드/디코드 절약분을 압도한다.
3. **인코딩 프리셋 → 기본값은 slow 유지, `--preset medium` 을 열어 뒀다.**
   캡처가 병목일 때는 프리셋이 전체 시간에 안 보였다(90.2 vs 87.8ms). 캡처를 바꾼 뒤에야
   차이가 난다: slow 28.6ms vs medium 23.6ms. 기본값을 slow 로 둔 것은 기존 결과물과
   바이트까지 같게 하기 위해서다. 전체 렌더로는 26.8s vs 24.1s, 파일 +2%.
4. **파이프라인 겹치기 → 이미 겹쳐 있었다.** ffmpeg 은 별도 프로세스라 인코딩은 원래
   캡처와 병행이다. 90.2ms(실전) 과 56ms(조각 합)의 차이가 그 경합 비용이었다.
5. **컷 수 < 코어 수 → 이제 무의미.** 캡처 교체 후 단일 프로세스가 4코어를 포화시켜
   **컷별 병렬 이득 자체가 사라졌다** (순차 26.8s = 병렬4 26.8s, medium 은 22.2 vs 24.1s).
   컷 분할·GOP 이어붙이기는 폐기.

| 전체 렌더 (956프레임) | 교체 전 | 교체 후 |
|---|---:|---:|
| 순차 `--all` | 93.0s | **26.8s** (medium 24.1s) |
| 컷별 병렬 4프로세스 | 45.0s | 26.8s — 이득 소멸 |

남은 여지: 브라우저 WebCodecs 로 h264 를 직접 뽑으면 PNG 단계가 사라지지만
baseline 프로파일 제약으로 화질 요건(crf 12, high)과 맞지 않아 보류.
근거는 benchmark 10~17번.
